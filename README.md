# Лабораторна робота №7–9
## Реалізація типізованого CRUD-сервісу: узагальнення, колекції та сортування

### 1. Мета роботи

Реалізувати типізований CRUD-сервіс на Java з використанням generics, колекцій, винятків, `Comparator`, wildcard-типів і сортування за кількома критеріями.

### 2. Предметна область

Проєкт моделює систему керування фітнес-клубом. Для лабораторної створено дві сутності:

- `ClientRecord` — клієнт: ID, ім'я, прізвище та вік;
- `SubscriptionRecord` — абонемент: ID, назва, тривалість у місяцях і ціна за місяць.

Обидві сутності успадковують `BaseEntity`, який зберігає спільні поля `id` і `name`. ID є незмінним після створення. Класи `Client` і `Subscription` з попередніх лабораторних залишені без видалення, щоб не ламати їхню логіку та демонстрації. Для цієї лабораторної `ClientRecord` і `SubscriptionRecord` є окремими моделями CRUD-сервісу.

### 3. Основні класи

- `BaseEntity` — абстрактний базовий клас з ID, ім'ям, `equals()`, `hashCode()` і `toString()`.
- `EntityNotFoundException` — виняток із полем `id` та інформативним повідомленням.
- `CRUDService<T extends BaseEntity>` — узагальнений контракт CRUD-операцій і загального сортування.
- `InMemoryCrudService<T extends BaseEntity>` — універсальна реалізація сервісу, яка працює з будь-яким підкласом `BaseEntity` без змін.
- `ClientRecordService` і `InMemoryClientRecordService` — спеціалізований сервіс клієнтів із сортуванням за ім'ям і віком.
- `SubscriptionRecordService` і `InMemorySubscriptionRecordService` — спеціалізований сервіс абонементів із сортуванням за назвою та місячною ціною.
- `CrudServiceDemo` — демонструє CRUD, сортування, виняток, wildcard та `Comparator<? super T>`.

### 4. Generics та обмеження типу

У `CRUDService<T extends BaseEntity>` параметр типу обмежений `BaseEntity`. Тому сервіс може без приведення типів викликати `getId()` і `getName()`, а компілятор забороняє передати сторонній тип, який не є сутністю.

У Java узагальнення працюють з посилальними типами, тому `CRUDService<long>` не допускається; для числового ID використовується примітив `long` усередині класу, а для параметрів generics — типи-обгортки на кшталт `Long`.

Не можна створити `new T()` або `new T[10]`, оскільки конкретний тип `T` недоступний для такого створення під час виконання. Тому сховище реалізовано як `Map<Long, T>`, без створення екземплярів чи масивів `T`.

### 5. CRUD і виняток

- `save(entity)` додає нову сутність або оновлює наявну за тим самим ID через `Map.put()`.
- `findById(id)` повертає сутність або кидає `EntityNotFoundException`.
- `delete(id)` повертає `true`, якщо запис був, і `false`, якщо його не існувало.
- `findAll()` повертає новий список, а не внутрішнє сховище.
- `save(null)` відхиляється через `IllegalArgumentException`.

`EntityNotFoundException` успадковує `RuntimeException`, тому є неперевіреним винятком. Відсутність запису — ситуація, яку викликач може обробити там, де це потрібно, без обов'язкового додавання `throws` до кожного методу.

### 6. Чому використано LinkedHashMap

Сховище — `LinkedHashMap<Long, T>`. ID є ключем, тому пошук, оновлення та видалення за ID у середньому мають складність `O(1)`. На відміну від `HashMap`, `LinkedHashMap` зберігає порядок вставлення, що зручно для демонстрації. Відсортовані результати будуються на копії списку, а внутрішнє сховище не змінюється.

| Операція | `ArrayList` | `HashMap` | `LinkedHashMap` | `TreeMap` |
|---|---|---|---|---|
| Пошук за ID | `O(n)` | `O(1)` у середньому | `O(1)` у середньому | `O(log n)` |
| Додавання | `O(1)` амортизовано в кінець | `O(1)` у середньому | `O(1)` у середньому | `O(log n)` |
| Оновлення за ID | `O(n)` для пошуку | `O(1)` у середньому | `O(1)` у середньому | `O(log n)` |
| Видалення за ID | `O(n)` | `O(1)` у середньому | `O(1)` у середньому | `O(log n)` |
| Відсортований список за полями сутності | `O(n log n)` | `O(n log n)` після копіювання | `O(n log n)` після копіювання | `O(n log n)` для сортування за полями; `TreeMap` автоматично впорядковує лише за ключем |
| Порядок обходу | За індексом | Не гарантується | Порядок вставлення | За ключем |

Складність хеш-таблиць наведено для типових умов і залежить від розподілу хешів. `TreeMap` не обрано, оскільки основна вимога — швидкий пошук за ID і можливість отримувати різні порядки сортування за полями сутності, а не постійне сортування за ключем.

### 7. Сортування та вибір Comparator

`findAllSortedByName()` є `default`-методом у `CRUDService`, оскільки кожна сутність має `name`. Він використовує `Comparator`, а не `Comparable`, щоб не нав'язувати класам сутностей один природний порядок: у різних сценаріях можна сортувати за різними полями.

Методи, залежні від конкретних полів, розміщені у спеціалізованих інтерфейсах:

- `ClientRecordService.findAllSortedByNameAndByAge()` — спочатку за ім'ям, при збігу імен — за віком;
- `SubscriptionRecordService.findAllSortedByNameAndByMonthlyPrice()` — спочатку за назвою, при збігу назв — за місячною ціною.

Ці методи не розміщені в загальному `CRUDService<T>`, бо не кожна сутність має вік або місячну ціну. Сортування використовує `thenComparingInt()` або `thenComparingDouble()`. Для абонементів у тестових даних є кілька записів із назвою `Стандартний`, але різними цінами, тому вторинне сортування можна побачити в результаті.

Обидва методи сортування використовують `findAllSorted()`. Цей метод створює копію списку й сортує її, не змінюючи сховище.

### 8. Чому `Comparator<? super T>`

`Comparator<? super T>` означає компаратор для `T` або будь-якого його батьківського типу. Наприклад, `Comparator<BaseEntity>` можна передати для сортування `ClientRecord`, оскільки `ClientRecord` успадковує `BaseEntity`. Якби параметр мав тип лише `Comparator<T>`, такий повторно використовуваний компаратор базового типу було б передати складніше.

### 9. equals() і hashCode()

`BaseEntity.equals()` перевіряє точний клас і ID. Тому сутності одного класу з однаковим ID вважаються рівними навіть за відмінності інших полів. Об'єкти різних класів із тим самим ID не вважаються рівними. `hashCode()` використовує ті самі значущі дані — клас і ID, отже узгоджений з `equals()`.

`Comparable` у цьому рішенні не реалізовано: порядок визначають `Comparator`, тож узгодженість `compareTo()` з `equals()` тут не застосовується. Компаратори за назвою й ціною можуть повернути `0` для двох різних сутностей, якщо всі поля сортування збігаються; це не робить об'єкти рівними й не впливає на сховище, бо воно не є `TreeSet`.

### 10. Wildcard `? extends BaseEntity`

Метод `printAll(Collection<? extends BaseEntity> items)` приймає колекцію `BaseEntity` або будь-якого її підкласу. `List<ClientRecord>` не є підтипом `List<BaseEntity>` через інваріантність generics. Wildcard дозволяє передати `List<ClientRecord>` без небезпечного приведення типів. Метод лише читає елементи колекції, що відповідає використанню `? extends`.

### 11. Перевірені сценарії

`CrudServiceDemo` демонструє:

- додавання клієнтів і абонементів;
- оновлення за тим самим ID без збільшення кількості записів;
- успішний пошук і обробку `EntityNotFoundException` для відсутнього ID;
- успішне й неуспішне видалення;
- сортування за ім'ям, віком і місячною ціною;
- повторювані назви абонементів для перевірки вторинного сортування;
- перевірку незмінності порядку й складу сховища після сортування;
- `printAll(Collection<? extends BaseEntity>)`;
- використання `Comparator<BaseEntity>` для `CRUDService<ClientRecord>`;
- узгодженість `equals()` і `hashCode()`.

### 12. Компіляція та запуск

Виконувати команди з кореневої папки `JavaFitnessClub` у PowerShell або терміналі:

```powershell
javac -d out src/*.java
java -cp out src.CrudServiceDemo
```

Додаткові демонстрації попередніх лабораторних можна запускати окремо, наприклад:

```powershell
java -cp out src.ClientCrudDemo
java -cp out src.SubscriptionDemo
java -cp out src.AdapterDemo
java -cp out src.ObserverDemo
```

Для компіляції потрібен JDK 21 або сумісний JDK, оскільки проєкт попередніх лабораторних використовує `sealed`-класи та switch pattern matching.
